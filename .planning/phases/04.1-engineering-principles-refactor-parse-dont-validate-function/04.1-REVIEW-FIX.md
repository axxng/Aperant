### WR-02: `rowToTask` uses fallback defaults (`?? 0`, `?? ''`) for required `pr_created` fields

**Files modified:** `apps/web/api/_lib/db/tasks.ts`
**Commit:** `de56de6c`
**Applied fix:** Replaced the `?? 0` / `?? ''` coercions in the `pr_created` branch of `rowToTask` with an explicit integrity check that throws `Error('DB integrity: pr_created task ${id} is missing required GitHub fields')` when any of `github_issue_number`, `github_issue_url`, or `github_repo` is null. This enforces the parse-don't-validate principle at the DB boundary and prevents silent propagation of empty values downstream.

---

### WR-03: `buildCreateTaskInput` uses `||` instead of `?? null`, silently dropping falsy-but-valid values

**Files modified:** `apps/web/api/_lib/db/tasks.ts`
**Commit:** `de56de6c`
**Applied fix:** Replaced all `|| null` usages with `?? null` for `priority`, `category`, `github_issue_number`, `github_issue_url`, `github_repo`, and `github_project_item_id` in `buildCreateTaskInput`. This preserves falsy-but-valid values (e.g. empty strings, `0`) instead of silently coercing them to `null`.

Note: WR-02 and WR-03 were both in `tasks.ts` and committed atomically in a single commit.

### WR-04: `github-sync.ts` defines a private `githubFetch` that bypasses rate-limit detection

**Files modified:** `apps/web/api/_lib/sync/github-sync.ts`
**Commit:** `269330bd`
**Applied fix:** Removed the local `GITHUB_API` constant and local `githubFetch` function. Added import of `githubFetch`, `GITHUB_API`, and `GitHubRateLimitError` from `'../github.js'`. Updated the `syncRepo` call site from `githubFetch(url, headers)` to `githubFetch(url, { headers })` to match the shared function's `RequestInit` signature. Retained the local `getGitHubToken` helper (using `resolveConfig`) because `syncGitHubProject` still makes raw GraphQL `fetch` calls that require it — replacing those would be a larger refactor out of scope for this finding.

### WR-05: `upsertTriageRecord` return type mismatch — `triageState` not included

**Files modified:** `apps/web/api/_lib/db/triage.ts`
**Commit:** `70c51a15`
**Applied fix:** Updated the return type of `upsertTriageRecord` from `Promise<TriageRecord>` to `Promise<TriageRecord & { triageState: TriageState }>`. The runtime already returns the full type (via `rowToTriage` through `getTriageRecord`); this fix makes the declared type match reality so TypeScript can enforce it for callers.

---

### WR-06: `github-writeback.ts` accesses `task.githubProjectItemId` without type narrowing

**Files modified:** `apps/web/api/_lib/sync/github-writeback.ts`
**Commit:** `05a62f27`
**Applied fix:** Added an explanatory comment above the `if (task.githubProjectItemId ...)` condition documenting that `githubProjectItemId` is an optional field on `TaskBase`, the falsy check is intentional, and no `pr_created` narrowing is required because any status variant can carry a project item ID once linked to a GitHub Project board. The comment approach was chosen over structural narrowing because the field is correctly defined on `TaskBase` (not exclusively on `pr_created`) and the runtime behaviour is sound.

---

### WR-07: `githubGraphQL` response is not parsed — raw `any` returned

**Files modified:** `apps/web/api/_lib/github.ts`
**Commit:** `ce96674f`
**Applied fix:** Added a detailed comment above `githubGraphQL` documenting this as a known limitation: each call site accesses deeply nested properties without Zod schema validation, which violates the parse-don't-validate principle. The comment explains the deferred remediation path (define per-query Zod schemas in `validation.ts`, parse at each call site or via a generic type parameter) and the reason for deferral (each query has a distinct response shape requiring separate schema definitions). Full schema enforcement is deferred to a future phase.
