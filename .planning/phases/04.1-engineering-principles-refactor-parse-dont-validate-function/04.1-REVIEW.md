## Summary

This review covers the Phase 04.1 refactor implementing four engineering principles across the `apps/web/` codebase: Parse-Don't-Validate, Functional Core / Imperative Shell, FSM / Illegal State Elimination, and Red-Green TDD. The refactor is largely well-executed — Zod schemas are consistently used at every untrusted boundary, the 4-step handler shape is applied uniformly across API routes, the discriminated union for `Task` correctly makes illegal states unrepresentable, and pure functions are extracted and co-located with tests.

The findings below are bugs and logic errors that survived the refactor. None are security vulnerabilities. The critical count is zero. Seven warnings identify correctness issues that can silently produce wrong behavior or dropped data; six info items flag code quality concerns.

## Warnings

### WR-01: Wrong variable used in `broadcastEvent` call — `status` instead of `validatedStatus`

**File:** `apps/web/api/tasks/order/[scope]/[status].ts:35`
**Issue:** The handler parses the `status` path param into `validatedStatus` (a validated `TaskStatusKey`), then calls `broadcastEvent('tasks_reordered', { scope, status })`. The reference `status` on line 35 resolves to the enclosing module scope, not the validated path param. At runtime in a Vercel serverless function this will likely be `undefined`, meaning the broadcast event payload will carry `{ scope, status: undefined }` — losing the column that was reordered.
**Fix:**
```typescript
// line 35 — replace `status` with `validatedStatus`
await broadcastEvent('tasks_reordered', { scope, status: validatedStatus });
```

### WR-02: `rowToTask` uses fallback defaults (`?? 0`, `?? ''`) for required `pr_created` fields, masking DB inconsistency

**File:** `apps/web/api/_lib/db/tasks.ts:69-71`
**Issue:** The `pr_created` branch of `rowToTask` coerces nullable DB columns to empty defaults:
```typescript
githubIssueNumber: parsed.github_issue_number ?? 0,
githubIssueUrl:    parsed.github_issue_url   ?? '',
githubRepo:        parsed.github_repo        ?? '',
```
The `Task` discriminated union (defined in `src/shared/types/task.ts:66`) requires `githubIssueNumber: number`, `githubIssueUrl: string`, and `githubRepo: string` as non-optional on `pr_created`. Coercing `null` to `0`/`''` produces a structurally valid TypeScript object that nonetheless carries meaningless data. Code downstream (GitHub writeback, URL rendering) that relies on `task.githubRepo` being a real `owner/repo` string will silently operate on an empty string. The correct behavior is to throw, matching the parse-don't-validate principle applied elsewhere in the file.
**Fix:**
```typescript
case 'pr_created':
  if (!parsed.github_issue_number || !parsed.github_issue_url || !parsed.github_repo) {
    throw new Error(
      `DB integrity: pr_created task ${parsed.id} is missing required GitHub fields`
    );
  }
  return {
    ...base,
    status: 'pr_created',
    githubIssueNumber: parsed.github_issue_number,
    githubIssueUrl:    parsed.github_issue_url,
    githubRepo:        parsed.github_repo,
  };
```

### WR-03: `buildCreateTaskInput` uses `||` instead of `?? null`, silently dropping falsy-but-valid values

**File:** `apps/web/api/_lib/db/tasks.ts:107-110`
**Issue:** Several fields use `|| null`:
```typescript
priority:              input.priority              || null,
category:              input.category              || null,
github_issue_number:   input.githubIssueNumber     || null,
github_project_item_id: input.githubProjectItemId  || null,
```
`||` coerces any falsy value to `null`. For `github_issue_number` this means issue `0` would be stored as `null` (GitHub issue numbers are 1-based so this is currently not exploitable, but it is a latent bug). More importantly, `priority`, `category`, and the string IDs use string values where the empty string `''` would also be silently discarded. The correct operator is `?? null`, which preserves any non-null/non-undefined value.
**Fix:**
```typescript
priority:               input.priority              ?? null,
category:               input.category              ?? null,
github_issue_number:    input.githubIssueNumber     ?? null,
github_issue_url:       input.githubIssueUrl        ?? null,
github_repo:            input.githubRepo            ?? null,
github_project_item_id: input.githubProjectItemId   ?? null,
```

### WR-04: `github-sync.ts` defines a private `githubFetch` that bypasses rate-limit detection from `_lib/github.ts`

**File:** `apps/web/api/_lib/sync/github-sync.ts:18-27`
**Issue:** `github-sync.ts` declares its own local `githubFetch` function (lines 18–27) instead of importing the exported `githubFetch` from `../_lib/github.ts`. The shared version in `github.ts` includes `GitHubRateLimitError` detection for 429 and 403 responses. The local version makes a plain `fetch` call with no rate-limit handling, so sync jobs will silently ingest GitHub error bodies as issue data when the token is rate-limited, instead of surfacing the error and backing off. Additionally, `github-sync.ts` duplicates `const GITHUB_API = 'https://api.github.com'` (line 10) which is already exported from `github.ts`.
**Fix:**
```typescript
// Remove the local githubFetch and GITHUB_API constant.
// Add to imports at the top of github-sync.ts:
import { githubFetch, GITHUB_API, GitHubRateLimitError } from '../github.js';

// Then in syncRepo, the existing call `await githubFetch(url, headers)` will
// automatically pick up rate-limit detection. Add error handling in the outer
// catch block for GitHubRateLimitError if needed.
```

### WR-05: `upsertTriageRecord` returns `TriageRecord` but the `triageState` discriminated union is not included in the return type

**File:** `apps/web/api/_lib/db/triage.ts:49-74`
**Issue:** The function signature declares `Promise<TriageRecord>` but `rowToTriage` (called internally via `getTriageRecord`) returns `TriageRecord & { triageState: TriageState }`. The non-null assertion `record!` on line 73 drops the `triageState` field from the return type at the type-system level because `getTriageRecord` returns `(TriageRecord & { triageState: TriageState }) | null`. Callers of `upsertTriageRecord` that need `triageState` get the correct runtime value but TypeScript cannot enforce it because the declared type omits `triageState`. This is a type mismatch between declared and returned type.
**Fix:**
```typescript
// Change the return type declaration on line 53:
export async function upsertTriageRecord(
  repo: string,
  issueNumber: number,
  updates: { isTriaged?: boolean; priority?: 'critical' | 'high' | 'medium' | 'low' | null }
): Promise<TriageRecord & { triageState: TriageState }> {
  // ... existing body unchanged ...
  const record = await getTriageRecord(repo, issueNumber);
  return record!; // TypeScript will now correctly infer the full type
}
```

### WR-06: `github-writeback.ts` accesses `task.githubProjectItemId` on a `Task` union type without narrowing

**File:** `apps/web/api/_lib/sync/github-writeback.ts:63`
**Issue:** `task.githubProjectItemId` is accessed on the `Task` discriminated union without first narrowing to a variant that carries it. `githubProjectItemId` is defined on `TaskBase` as `optional`, so TypeScript permits the access, but the behavior is surprising: only the `pr_created` variant is guaranteed to have `githubRepo` and `githubIssueNumber` populated on the discriminated union. The condition `if (task.githubProjectItemId && changes.status !== undefined)` (line 63) will evaluate to false when the item ID is `undefined`, which is correct in practice, but is relying on a runtime falsy check rather than on type narrowing. This becomes a correctness gap if the type shape changes. Not a crash today, but an inconsistency with the parse-don't-validate principles applied elsewhere.
**Fix:** Narrow with `task.status === 'pr_created'` before accessing `task.githubProjectItemId`, or annotate the access with a comment explaining that the optional field is safe to access here and why.

### WR-07: `github.ts` `githubGraphQL` response is not parsed — raw `any` used from GitHub GraphQL endpoint

**File:** `apps/web/api/_lib/github.ts:61-77`
**Issue:** `githubGraphQL` fetches from the GitHub GraphQL endpoint and returns `data.data` as an untyped `any`. Callers (`github-writeback.ts`, `github-sync.ts`, `github/projects/[owner]/[number]/index.ts`, etc.) then access deeply nested properties without any schema validation (e.g. `data.user?.projectV2`, `data.fields.nodes.find(...)`). This violates the parse-don't-validate principle applied at all other external API boundaries. A change in the GitHub GraphQL schema (or a partial error response that still has `data: {}`) will silently produce `undefined` propagation rather than a detectable schema error. Note: this is a quality/correctness concern, not a security vulnerability, as the data flows inward from GitHub only.
**Fix:** Define a Zod schema in `validation.ts` for each GraphQL response shape used (project info, project items) and parse the response via `schema.parse(data)` in each call site or within `githubGraphQL` via a generic type parameter.

### IN-03: `Task` type — `reviewReason` is required on `ai_review` and `human_review` variants but DB rows may be `null`

**File:** `apps/web/src/shared/types/task.ts:63-64` and `apps/web/api/_lib/db/tasks.ts:60-62`
**Issue:** The discriminated union requires `reviewReason: ReviewReason` (non-optional, non-null) on `ai_review`, `human_review`, and `error` variants. However, `rowToTask` casts these with `as Task` after assigning `reviewReason: parsed.review_reason ?? undefined`. The TypeScript compiler accepts this because of the cast, but a DB row with `status = 'ai_review'` and `review_reason = null` will produce a runtime object where `reviewReason` is `undefined` while the type contract promises `ReviewReason`. This means the discriminated union claim of "illegal states unrepresentable" is partially undermined by the `as Task` cast.
**Fix:** Either make `reviewReason` optional (`reviewReason?: ReviewReason`) on those variants (relaxing the invariant), or throw when `review_reason` is null for these statuses (enforcing it strictly):
```typescript
case 'ai_review':
  if (!parsed.review_reason) throw new Error(`ai_review task ${parsed.id} missing review_reason`);
  return { ...base, status: 'ai_review', reviewReason: parsed.review_reason };
```
The test at `tasks.test.ts:60-65` already documents the lenient behavior as expected, so if the decision is to keep it lenient, update the type to `reviewReason?: ReviewReason`.

### IN-04: `safeJsonParse` silently swallows parse errors — inconsistent with parse-don't-validate principle

**File:** `apps/web/api/_lib/db/tasks.ts:7-14` and `apps/web/api/_lib/db/products.ts:7-14`
**Issue:** `safeJsonParse` returns a fallback value on any JSON parse error, including when the DB column contains corrupt data. This means a task with `labels = 'not-json'` will silently return `[]` instead of surfacing a data integrity error. This is inconsistent with the explicit principle (stated in CLAUDE.md) that DB row parse failures should throw (programmer/deployment bugs are not user-recoverable). The function is used for `labels`, `assignees`, `metadata`, `milestone`, and `sources` — all columns that come from the DB boundary that `taskDbRowSchema.parse(row)` validated the outer shape of, but not the JSON content within.
**Fix:** For fields that must always be valid JSON (labels, assignees, sources), throw instead of returning the fallback, or validate the parsed result against a Zod schema. The `safeJsonParse` helper is appropriate only for fields where the fallback is semantically correct (e.g., when null is an accepted DB value and the parsed result would be discarded anyway).
