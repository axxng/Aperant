# Phase 04.2: Code Review Report

**Reviewed:** 2026-04-22T00:00:00Z
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

This phase adds a local dev mock environment: SQLite fallback via `MOCK_SERVICES` env var, Express middleware registering GitHub API fixtures and an OAuth bypass, a deterministic seed script using faker, and a frontend dev-mode banner. The overall structure is sound — the seed guard, the dev-server gating, and the frontend banner check are all in the right places. Two critical issues exist around production blast-radius: `client.ts` has no Vercel guard on `MOCK_SERVICES`, and `registerMockRoutes` has no internal self-protection, creating an unsafe public API. One concurrency warning exists in the migration runner. Four info-level items cover a silent auth error, an implicit Vite env var, a type cast inconsistency with project conventions, and minor cookie parsing notes.

## Critical Issues

### CR-01: `client.ts` has no production guard on `MOCK_SERVICES`

**File:** `apps/web/api/_lib/db/client.ts:8-10`

**Issue:** If `MOCK_SERVICES=true` is accidentally configured in a Vercel deployment (e.g., via a misconfigured env var or a copy-paste from `.env.local`), `getClient()` silently falls back to `file:dev.db` — a local SQLite path that does not exist on Vercel's serverless filesystem. All DB operations would fail with cryptic errors rather than an early, explicit startup failure. Compare this with `api/_lib/auth/jwt.ts:4-6`, which throws at module load time when `JWT_SECRET` is missing and `process.env.VERCEL` is set. The same pattern is needed here.

**Fix:**
```typescript
export function getClient(): Client {
  if (!client) {
    if (process.env.MOCK_SERVICES === 'true') {
      // Hard-fail in production — MOCK_SERVICES must never be set on Vercel
      if (process.env.VERCEL) {
        throw new Error(
          'MOCK_SERVICES=true is not allowed in production (VERCEL env detected). ' +
          'Remove MOCK_SERVICES from your Vercel environment variables.'
        );
      }
      client = createClient({ url: 'file:dev.db' });
    } else {
      client = createClient({
        url: process.env.TURSO_DATABASE_URL!,
        authToken: process.env.TURSO_AUTH_TOKEN,
      });
    }
  }
  return client;
}
```

### CR-02: `registerMockRoutes` has no internal guard — unsafe public API

**File:** `apps/web/scripts/mocks/github-fixtures.ts:106-162`

**Issue:** `registerMockRoutes` exposes an unauthenticated OAuth bypass route (`GET /api/auth/github/callback`) that creates or upserts a user and issues a valid JWT. Its only protection against production activation is the call-site guard in `dev-server.ts:58`. The function itself has no internal check. This is fragile: if the function is imported and called in any other context — a test setup file, a future middleware aggregator, or even by mistake — the bypass activates silently. The mock OAuth callback does not even require a `state` parameter or code, making it a full authentication bypass for any user who can reach the endpoint.

**Fix:** Add a runtime guard at the top of `registerMockRoutes` so the function is safe regardless of caller:

```typescript
export function registerMockRoutes(app: Application): void {
  if (process.env.MOCK_SERVICES !== 'true') {
    throw new Error(
      '[mock] registerMockRoutes called without MOCK_SERVICES=true. ' +
      'This function must never run in production.'
    );
  }

  // Mock OAuth initiate — redirect directly to callback (no real GitHub redirect)
  app.get('/api/auth/github', (_req: Request, res: Response) => {
    res.redirect(302, '/api/auth/github/callback');
  });
  // ... rest of routes unchanged
}
```

This ensures that even if the import is made from an unexpected location, an exception is thrown at registration time rather than silently serving an auth bypass.

## Warnings

### WR-01: Race condition in `runMigrations` — no concurrency guard

**File:** `apps/web/api/_lib/db/client.ts:22-26`

**Issue:** `ensureDb()` checks `migrated` before awaiting `runMigrations()`. Because `migrated` is only set to `true` after the async call completes (line 25), two concurrent cold requests in the dev-server can both enter `runMigrations()` simultaneously. Migrations using `CREATE TABLE IF NOT EXISTS` survive this, but the `INSERT INTO migrations (name)` at line 44 will throw a UNIQUE constraint violation on the second concurrent call for the same migration name. The error propagates as an unhandled rejection from `ensureDb()` and returns a 500 to one of the two requests.

This is low-impact in practice (dev-server only, race window is milliseconds on startup), but it is a real bug that will surface under parallel test runs or rapid page reloads.

**Fix:** Use a promise-based lock so concurrent callers wait on the same migration run:

```typescript
let migrationPromise: Promise<void> | null = null;

export async function ensureDb(): Promise<Client> {
  const c = getClient();
  if (!migrationPromise) {
    migrationPromise = runMigrations(c).then(() => { migrated = true; });
  }
  await migrationPromise;
  return c;
}
```

## Info

### IN-01: Silent `catch(() => {})` swallows OAuth token verification errors

**File:** `apps/web/src/client/App.tsx:49`

**Issue:** When the OAuth callback injects a `?token=` query param, the fetch to `/api/auth/me` is caught with an empty handler. Any network error, unexpected response shape, or server error causes `user` to be `null` and `setAuth` is never called — the user is left on the login page with no feedback and no log entry. This makes debugging OAuth failures in the dev mock flow very difficult.

**Fix:**
```typescript
.catch((err) => {
  console.warn('[auth] OAuth token verification failed:', err);
})
```

### IN-02: `VITE_MOCK_SERVICES` is not declared in `vite.config.ts` — implicit injection

**File:** `apps/web/vite.config.ts`

**Issue:** `DevModeBanner` reads `import.meta.env.VITE_MOCK_SERVICES`. This works because Vite automatically exposes all `VITE_*`-prefixed env vars from `.env` files. However, there is no explicit `define` block or `envPrefix` configuration in `vite.config.ts` documenting this variable. Future developers may not realize that `VITE_MOCK_SERVICES` must be set separately from `MOCK_SERVICES` (the server-side var) in `.env.local`. The `.env.example` does document both, but the config file itself gives no indication.

**Fix:** Add an `envPrefix` comment or a `define` block to make the dependency explicit, or at minimum add a comment in `vite.config.ts`:

```typescript
// VITE_MOCK_SERVICES is consumed by DevModeBanner via import.meta.env.
// It must be set alongside server-side MOCK_SERVICES in .env.local.
// See .env.example for the required pairing.
```

### IN-03: Raw DB row cast in `runMigrations` violates parse-don't-validate convention

**File:** `apps/web/api/_lib/db/client.ts:39`

**Issue:** `result.rows.map((r: any) => r.name as string)` is a blind type cast on a raw DB row. If the `migrations` table schema changes or a row is corrupted, this silently returns `undefined` cast to `string`, and the migration deduplication check (`applied.has(migration.name)`) would silently fail to skip already-applied migrations. This is inconsistent with the project's "parse-don't-validate" principle (CLAUDE.md engineering principles §1), which requires `rowSchema.parse(row)` at every DB boundary.

**Fix:**
```typescript
import { z } from 'zod';
const migrationRowSchema = z.object({ name: z.string() });

const applied = new Set(
  result.rows.map((r) => migrationRowSchema.parse(r).name)
);
```

### IN-04: `parseCookies` does not handle missing `k` segment defensively

**File:** `apps/web/scripts/dev-server.ts:26-29`

**Issue:** `const [k, ...v] = c.split('=')` — if a cookie string is malformed and contains no `=` (e.g., a bare token), `k` is the whole string and `v` is `[]`, so `v.join('=')` returns `''`. This is silently discarded into the cookie map as `{ [token]: '' }` with no error. This is not a security issue (malformed cookies are ignored), but `k.trim()` is called without a null check — in standard JS, `k` can never be `undefined` from destructuring an array, so this is safe. Note for future maintainers: the parser does not support quoted cookie values (RFC 6265 §4.1.1). This is acceptable for a dev-only server.

**Fix:** No code change required. Consider adding a comment:
```typescript
// Note: simplified parser — does not handle quoted cookie values. Dev server only.
```
