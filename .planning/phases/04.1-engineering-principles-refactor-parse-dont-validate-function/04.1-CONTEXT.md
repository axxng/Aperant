# Phase 04.1: Engineering Principles Refactor - Context

**Gathered:** 2026-04-21
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase refactors the existing web app codebase to enforce four core engineering principles, then codifies them as standing standards in CLAUDE.md so all future phases inherit them automatically:

1. **Parse-don't-validate** — Parse raw input into typed domain objects at every untrusted boundary; reject immediately on failure; never do runtime type checks inside domain logic.
2. **Functional core / imperative shell** — Pure functions carry business logic (no I/O, deterministic); a thin imperative shell orchestrates I/O and delegates to pure functions. Every handler follows: parse input → authorize → call pure domain functions → respond.
3. **FSM / Illegal state elimination** — Discriminated unions make invalid states unrepresentable. Every domain object that has lifecycle state gets a typed state machine.
4. **Red-green TDD** — Write a failing test before writing implementation for every function being refactored. Going forward, all new code must have tests written first.

No new user-facing features ship in this phase. Output is cleaner code + CLAUDE.md engineering standards.

</domain>

<decisions>
## Implementation Decisions

### Parse-Don't-Validate

- **D-01:** Zod parsing applies at **all untrusted data boundaries** — not just API input, but also:
  - DB row → domain type mappers (e.g. `rowToTask()` currently uses blind `as TaskStatus` casting → replace with `z.parse()`)
  - Raw GitHub API JSON responses (e.g. `mapGitHubIssue()`, `mapGitHubPR()` currently use `as any` field access → add Zod schemas)
  - API input boundaries already covered by `validation.ts` — keep and extend
- **D-02:** On parse failure: use `z.parse()` (throws `ZodError`); the handler's `try/catch` surfaces a 500. Parse errors are programmer/deployment bugs, not user-recoverable errors — no null-returning or Result wrappers needed.

### Functional Core / Imperative Shell

- **D-03:** Extracted pure functions **stay in the same file** as the handler that uses them — no new `*-logic.ts` files. Separate with a clear `// === Pure domain logic ===` comment block so the split is visible without creating extra modules.
- **D-04:** All four areas of the codebase get functional core treatment:
  - **Auth callback** — extract `determineRole()`, `buildEmailFallback()`, `buildUserRecord()` as pure functions
  - **GitHub API mappers** — `mapGitHubIssue()` and `mapGitHubPR()` are already pure; confirm they stay pure and add Zod input validation
  - **All API route handlers** — every handler restructured to the standard 4-step shape
  - **DB task queries** — extract pure record-building (data assembly) from SQL mutation in `createTask()`, `updateTask()`
- **D-05:** Every API handler follows the **standard 4-step shape** without exception:
  1. Parse input (Zod schema)
  2. Authorize (`authenticateRequest` + `hasRole`)
  3. Call pure domain function(s)
  4. Respond (res.json / res.status)

### Red-Green TDD

- **D-06:** **Retrofit + going forward** — write tests for every function being refactored in this phase BEFORE writing the refactor (red → green). Functions not touched by this refactor are not required to have tests added now. Going forward (Phase 5+), all new code must have a failing test written first.
- **D-07:** Test runner: **Vitest**. New test files co-located next to source (`api/_lib/db/tasks.test.ts`, `api/_lib/github.test.ts` already exists as pattern). Run with `cd apps/web && npm test`.

### FSM / Illegal State Elimination

- **D-08:** Four domains get FSM / discriminated union treatment:
  1. **Task status** — full discriminated union (see D-09)
  2. **GitHub sync state** — replace `githubSyncPending: boolean` + `githubSyncRetryCount: number` with a discriminated union: `SyncIdle | SyncPending | SyncRetrying | SyncComplete | SyncFailed`
  3. **Triage state** — model as discriminated union: `TriageUntouched | TriagePrioritized | TriageComplete`
  4. **OAuth callback state** — model the callback flow as explicit state machine steps: `NoCode → CodeReceived → TokenExchanged → UserFetched → Complete`, each returning the next state or an error
- **D-09:** Task status FSM uses **all states fully typed** — every `TaskStatus` variant becomes its own discriminated union member carrying only its valid fields. For example:
  - `error` state must carry `reviewReason`
  - `pr_created` state requires `githubIssueNumber`, `githubIssueUrl`, `githubRepo`
  - `ai_review` / `human_review` states require `reviewReason`
  - `backlog` / `queue` states do not carry GitHub sync fields as required
  This requires touching every component that reads the `Task` type — high surface area but the user explicitly wants full type safety.

<specifics>
## Specific Ideas

- **Discriminated union for Task:** Keep the DB flat structure; `rowToTask()` assembles the correct union variant based on `status` column value. Zod `discriminatedUnion('status', [...])` can handle this at parse time.
- **GitHub sync discriminated union:** `type GithubSyncState = { kind: 'idle' } | { kind: 'pending' } | { kind: 'retrying'; retryCount: number } | { kind: 'failed'; lastError: string; retryCount: number } | { kind: 'complete' }`. Replaces two separate Task fields.
- **OAuth state machine:** Each step is a pure function taking the previous state and returning the next state or an error: `receiveCode(req) → CodeState`, `exchangeToken(state) → TokenState`, etc. The handler calls them in sequence.
- **4-step handler shape example:**
  ```ts
  // 1. Parse
  const params = githubOwnerRepoSchema.parse(req.query);
  // 2. Authorize
  const user = await authenticateRequest(req, res);
  if (!user) return;
  // 3. Pure logic
  const result = buildIssueListResponse(rawIssues, params);
  // 4. Respond
  return res.json(result);
  ```

</specifics>
