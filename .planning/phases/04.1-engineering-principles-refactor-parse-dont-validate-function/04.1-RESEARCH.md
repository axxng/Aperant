### Locked Decisions

**D-01:** Zod parsing applies at all untrusted data boundaries — DB row→domain type mappers, raw GitHub API JSON responses, and API input (already partially covered).

## Summary

Phase 04.1 is a cross-cutting refactor with no new user-facing features. It applies four engineering principles uniformly across the `apps/web` backend API and shared type layer. The codebase has 28 route handler files, 5 DB layer modules, 2 GitHub utility files, and 9 frontend TypeScript files that reference `Task` or `TaskStatus` — all of which are within scope.

The highest-risk item is the Task discriminated union change (D-09). The `TaskStatus` type is currently a flat string union; converting it to a discriminated union cascades to `rowToTask()`, `task-store.ts`, `KanbanBoard.tsx`, `TaskCard.tsx`, `TaskEditDialog.tsx`, and `useKanbanFilters.ts`. The DB schema is unchanged — the discriminated union is a TypeScript-only representation layer. The `rowToTask()` mapper becomes the assembly point that reads the flat DB row and constructs the correct union variant.

The second major risk is the OAuth callback state machine (D-08 item 4). The current `callback.ts` is a 82-line monolith that mixes HTTP I/O (fetch, cookies, redirect) with domain logic (role determination, email fallback, user record assembly). Extracting pure functions here while preserving the existing test expectations (5 passing tests in `callback.test.ts`) requires careful sequencing.

**Primary recommendation:** Tackle the discriminated union change (Task type + `rowToTask()`) in Wave 1 as a pure type-and-mapper change; then refactor handlers in Wave 2; then the functional core / OAuth state machine in Wave 3; then add Zod schemas for DB mappers and GitHub responses in Wave 4; then codify CLAUDE.md in Wave 5.

### 6. GitHub Sync State Discriminated Union (D-08 item 2)

Current flat fields in `Task`:
```typescript
githubSyncPending?: boolean;
githubSyncRetryCount?: number;
```

Target discriminated union (from CONTEXT.md D-08 specifics):
```typescript
type GithubSyncState =
  | { kind: 'idle' }
  | { kind: 'pending' }
  | { kind: 'retrying'; retryCount: number }
  | { kind: 'failed'; lastError: string; retryCount: number }
  | { kind: 'complete' };
```

**DB impact:** DB schema is unchanged. The columns `github_sync_pending` (INTEGER) and `github_sync_retry_count` (INTEGER) remain. The `rowToTask()` mapper assembles the `GithubSyncState` variant from these two DB columns:
- `github_sync_pending = 0, github_sync_retry_count = 0` → `{ kind: 'idle' }`
- `github_sync_pending = 1, github_sync_retry_count = 0` → `{ kind: 'pending' }`
- `github_sync_pending = 1, github_sync_retry_count > 0` → `{ kind: 'retrying'; retryCount }`
- `github_sync_pending = 0, github_sync_retry_count > 0` → `{ kind: 'failed'; retryCount }` (needs `lastError` field — consider if DB needs it or if we skip)

**Problem flagged:** The `GithubSyncState.failed` variant in CONTEXT.md carries `lastError: string`, but there is no `last_sync_error` column in the DB schema. The DB has no migration for this. **Resolution needed before planning:** Either (a) add migration 013 to add `github_sync_error TEXT` column, or (b) define `failed` variant without `lastError` initially. This is a planning decision — flagged as an open question.

**Write-back code impact:** `tasks/[id]/index.ts` and `tasks/[id]/status.ts` currently call `updateTask(id, { githubSyncPending: true })` and `updateTask(id, { githubSyncPending: false, githubSyncRetryCount: 0 })`. After the discriminated union, `UpdateTaskInput` will need to accept a `githubSyncState?: GithubSyncState` field, which the DB update function translates back to flat columns. Alternatively, keep `githubSyncPending` and `githubSyncRetryCount` in `UpdateTaskInput` only (private internal API, not exposed externally) and only expose `GithubSyncState` in the read-model `Task` type.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Runtime type validation | Manual `typeof` guards, `instanceof` checks, or `as T` casts | `z.parse()` from Zod | Zod generates TypeScript types from schemas; custom guards drift from types |
| Discriminated union at parse time | Manual if/else switch on status before constructing object | `z.discriminatedUnion('status', [...])` | Zod handles discriminator dispatch and narrows types automatically |
| Exhaustive switch guards | Manual `throw new Error('unhandled')` clauses | TypeScript `satisfies` or `never` type | Compiler enforces exhaustiveness at build time |
| Test mocking of Vercel Request/Response | Custom mock classes | `vi.fn()` pattern from existing `callback.test.ts` | Pattern already established in codebase |

**Key insight:** Zod's `z.discriminatedUnion('status', [...variants])` can parse a flat DB row directly into the correct discriminated union variant. The `rowToTask()` function becomes a one-liner: `return taskRowSchema.parse(row)` where `taskRowSchema` is a discriminated union schema with the `status` column as discriminator.

## Common Pitfalls

### Pitfall 1: Flat TaskStatus in TaskOrderState

**What goes wrong:** `TaskOrderState = Record<TaskStatus, string[]>` is keyed by all 8 status strings. After the discriminated union refactor, `TaskStatus` is no longer a simple string union — it's a union of literal `{ status: 'backlog' }` objects. `Record<TaskStatus, ...>` will break.

**Why it happens:** `TaskOrderState` is defined in `task.ts` alongside `Task`. When `TaskStatus` changes from a string union to a discriminated union, downstream `Record<TaskStatus, string[]>` keyed types break at the TypeScript level.

**How to avoid:** Keep a separate `TaskStatusKey` string literal union (the 8 status strings) for use in `Record<>` keys and in the Kanban column config arrays. The discriminated union `Task` type uses the literal string `status` field discriminator rather than a separate type. Example pattern:
```typescript
// Keep the string union for keying
export type TaskStatusKey = 'backlog' | 'queue' | 'in_progress' | ...;

// Use as discriminator field in union
export type Task =
  | { status: 'backlog'; ... }
  | { status: 'error'; reviewReason: ReviewReason; ... }
  | ...;

// TaskOrderState uses the key union, not the discriminated union
export type TaskOrderState = Record<TaskStatusKey, string[]>;
```

### Pitfall 2: Frontend `task.status` string comparisons

**What goes wrong:** `KanbanBoard.tsx` has `mapToDisplayStatus(task.status)` and the `Record<TaskStatus, Task[]>` grouped object. After the union change, `task.status` is still a string literal (it's the discriminator field), so `task.status === 'backlog'` comparisons continue to work. The issue is that `Record<TaskStatus, ...>` where `TaskStatus` is now the union type (not a string) will cause TypeScript errors.

**How to avoid:** See Pitfall 1. Use `TaskStatusKey` for all `Record<>` definitions and enum-like arrays. `task.status` remains a string at runtime.

### Pitfall 3: `GithubSyncState.failed` missing `lastError` column

**What goes wrong:** CONTEXT.md defines `GithubSyncState.failed` with a `lastError: string` field, but the DB has no column for this. Attempting to populate it from `rowToTask()` will fail.

**How to avoid:** Either add migration 013 `ALTER TABLE tasks ADD COLUMN github_sync_error TEXT`, or redefine `failed` variant as `{ kind: 'failed'; retryCount: number }` without `lastError` for now. This must be resolved before the discriminated union implementation starts.

### Pitfall 4: Z.parse() in `rowToTask()` throws on any bad row

**What goes wrong:** If any existing DB rows have unexpected values (e.g., a `status` value not in the enum), `z.parse()` throws a `ZodError` and surfaces as a 500 to the frontend — potentially crashing task list views.

**How to avoid:** Before switching `rowToTask()` to `z.parse()`, run a data audit query: `SELECT DISTINCT status FROM tasks;`. Confirm all values are in the expected enum. The 8 values are known from the schema; any deviation is a real bug that needs fixing.

### Pitfall 5: Pure functions in same-file break existing `vi.mock()` patterns

**What goes wrong:** When pure functions are extracted within `callback.ts`, existing tests that `vi.mock('./callback.js')` won't automatically test the pure functions. The pure functions need their own `describe` blocks importing them directly.

**How to avoid:** The pure functions are exported. Tests import them directly from the source file. Handler tests that mock at the I/O level (`fetch`, `upsertOAuthUser`) continue to work as before.

### Pitfall 6: `updateTaskSchema` in `validation.ts` still has flat sync fields

**What goes wrong:** `updateTaskSchema` has `githubSyncPending: z.boolean().optional()` — this is the API input schema (client → server). After the discriminated union refactor, clients cannot directly set `githubSyncPending`. This field is an internal write-back concern only.

**How to avoid:** Remove `githubSyncPending` from `updateTaskSchema` (it should not be a client-settable field). The write-back handlers (`tasks/[id]/index.ts`, `tasks/[id]/status.ts`) update sync state directly via internal DB calls, not through the public update API.

const taskDbRowSchema = z.object({

  title: z.string(),
  description: z.string(),
  status: z.enum(['backlog', 'queue', 'in_progress', 'ai_review', 'human_review', 'done', 'pr_created', 'error']),

  priority: z.enum(['low', 'medium', 'high', 'urgent']).nullable().optional(),
  category: z.enum([...]).nullable().optional(),
  github_issue_number: z.number().nullable().optional(),
  github_issue_url: z.string().nullable().optional(),
  github_repo: z.string().nullable().optional(),
  github_project_item_id: z.string().nullable().optional(),
  labels: z.string().nullable().optional(),         // JSON string
  assignees: z.string().nullable().optional(),      // JSON string
  metadata: z.string().nullable().optional(),       // JSON string
  github_sync_pending: z.number(),                  // 0 or 1
  github_sync_retry_count: z.number(),
  created_at: z.string(),
  updated_at: z.string(),
});

function rowToTask(row: unknown): Task {
  const parsed = taskDbRowSchema.parse(row); // throws ZodError on bad row
  // assemble discriminated union variant based on parsed.status
  const base: TaskBase = {
    id: parsed.id,
    productId: parsed.product_id,
    // ... etc
    githubSyncState: buildSyncState(parsed.github_sync_pending, parsed.github_sync_retry_count),
  };
  switch (parsed.status) {
    case 'error':
    case 'ai_review':
    case 'human_review':
      return { ...base, status: parsed.status, reviewReason: parsed.review_reason! };
    case 'pr_created':
      return { ...base, status: 'pr_created', githubIssueNumber: parsed.github_issue_number!, githubIssueUrl: parsed.github_issue_url!, githubRepo: parsed.github_repo! };
    default:
      return { ...base, status: parsed.status };
  }
}

function buildSyncState(pending: number, retryCount: number): GithubSyncState {
  if (pending === 1 && retryCount === 0) return { kind: 'pending' };
  if (pending === 1 && retryCount > 0) return { kind: 'retrying', retryCount };
  if (pending === 0 && retryCount > 0) return { kind: 'failed', retryCount };
  return { kind: 'idle' };
}

  return res.json(task);
}

## Open Questions (RESOLVED)

1. **`GithubSyncState.failed` and `lastError` field**
   - What we know: CONTEXT.md defines `GithubSyncState.failed` with `lastError: string`, but no DB column exists for it.
   - What's unclear: Should migration 013 be added in this phase? Or should `failed` be defined as `{ kind: 'failed'; retryCount: number }` without `lastError`?
   - Recommendation: Define `failed` without `lastError` for this phase (TypeScript-only change, no DB migration needed). Add `lastError` in a future phase when the DB column is ready.
   - RESOLVED: Define `failed` variant as `{ kind: 'failed'; retryCount: number }` — no `lastError` field, no DB migration needed in this phase.

2. **`TriageState.complete` mapping rule**
   - What we know: `is_triaged = 1` with `priority = null` is currently a valid DB state (user marks as triaged but doesn't assign priority).
   - What's unclear: Should this map to `{ kind: 'prioritized' }` (which requires a priority) or `{ kind: 'complete' }`?
