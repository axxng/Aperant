# Phase 04.2: Fake Data and Mocked Services for Dev Env - Context

**Gathered:** 2026-04-22
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase establishes a self-contained local development environment for `apps/web/` — developers can run the full app without real Turso credentials, a real GitHub OAuth app, or any real external service. It delivers:

1. **Local SQLite DB** — `@libsql/client` file-mode (`file:dev.db`) used when `MOCK_SERVICES=true`
2. **GitHub API fixture mocks** — Express middleware in `dev-server.ts` intercepts `/api/github/*` and `/api/auth/github*` routes and returns realistic fixture responses
3. **Faker-based seed script** — Deterministic fake data generation populating the local DB with products, tasks, issues (triaged/untriaged/open/closed), labels, assignees, and tasks in all Kanban statuses
4. **CLAUDE.md codification** — The mock-services principle is codified as a standing standard (with examples) in root CLAUDE.md so all future phases inherit it

No new user-facing features ship in this phase. Output is a dev environment that works without credentials + CLAUDE.md engineering standards.

</domain>

<decisions>
## Implementation Decisions

### DB Layer Mock

- **D-01:** When `MOCK_SERVICES=true`, `client.ts` switches to `url: 'file:dev.db'` (local SQLite via `@libsql/client`). No new dependency — `@libsql/client` supports file mode natively. When `MOCK_SERVICES` is absent or false, real `TURSO_DATABASE_URL` is used unchanged.
- **D-02:** `dev.db` is gitignored. Each developer seeds their own local DB by running the seed script. No binary blobs in git.
- **D-03:** Migrations run on `ensureDb()` as normal — same migration path as production. The local SQLite DB goes through the same schema as Turso.

### GitHub API Mock

- **D-04:** GitHub API mocking is done via Express route middleware in `scripts/dev-server.ts`. When `MOCK_SERVICES=true`, the dev server registers mock routes for GitHub API paths before loading real handlers. Real source files are not modified.
- **D-05:** Mock routes are registered in a dedicated `scripts/mocks/github-fixtures.ts` file (or inline in dev-server.ts) — separate from source code so the mock layer is clearly identifiable and deletable.
- **D-06:** Endpoints that need mocks:
  - `GET /api/github/repos/:owner/:repo/issues` — per-repo issue list
  - Cross-repo fan-out (served by AllIssuesView querying all products — the per-repo mock above covers this)
  - `GET /api/github/repos/:owner/:repo/labels` — label list for filter bar
  - OAuth flow: `GET /api/auth/github` and `GET /api/auth/github/callback` — bypassed in mock mode
- **D-07:** Mock OAuth is a **one-click bypass**: in mock mode, `GET /api/auth/github/callback` immediately creates/returns a seeded admin user session (issues a JWT for the seeded admin user). No redirect to github.com, no real OAuth app needed.

### Seed Data

- **D-08:** Seed uses `@faker-js/faker` as a **dev dependency** (not production dependency). Seed script lives at `scripts/seed.ts`.
- **D-09:** Seed is **deterministic** via `faker.seed(12345)`. Same data on every run. Reproducible dev env, easier to debug UI states.
- **D-10:** Seed creates a **realistic dataset** covering all UI states:
  - 3 products (different colors, different connected repos)
  - 30–50 issues per product (mix of open and closed issues)
  - Issues with multiple labels and assignees (exercises filter bar)
  - Some issues with triage state (priority set, `is_triaged=true`) — exercises triage badges
  - Some issues untriaged — exercises the default untouched state
  - Tasks in all Kanban statuses: `backlog`, `queue`, `in_progress`, `done`, `error`, `ai_review`, `human_review`, `pr_created`
  - A seeded admin user (used by mock OAuth bypass)

### Activation

- **D-11:** Mock mode is activated by setting `MOCK_SERVICES=true` in `.env.local`. Both `scripts/dev-server.ts` and Vite (via `VITE_MOCK_SERVICES`) read this flag. When `MOCK_SERVICES` is absent, the app uses real services normally.
- **D-12:** `.env.local` is already gitignored. Developers set `MOCK_SERVICES=true` once locally. No committed env file carries this flag — it's an explicit opt-in.
- **D-13:** A visible "Dev Mode" banner or indicator appears in the UI when `VITE_MOCK_SERVICES=true` is set, so developers know they're in mock mode.

### CLAUDE.md Codification

- **D-14:** The CLAUDE.md engineering principle follows the **same format as Phase 04.1** — principle statement + concrete examples + anti-pattern pairs. It covers:
  - The principle: every external service (DB, GitHub, OAuth) must have a dev mock available
  - How DB is mocked: `MOCK_SERVICES=true` → `file:dev.db` in `client.ts`
  - How GitHub is mocked: fixture middleware in `dev-server.ts`
  - How to seed: `cd apps/web && npx tsx scripts/seed.ts`
  - Anti-pattern: hardcoding `process.env.TURSO_DATABASE_URL!` without a mock fallback

### Claude's Discretion

- Exact faker quantity (30 vs 50 issues per product) — use judgement based on what covers all filter/pagination states
- File structure for fixture data (`scripts/mocks/` vs `scripts/fixtures/`) — keep it clean and separate from source

</decisions>

## Existing Code Insights

### Reusable Assets
- `@libsql/client` — already installed; supports `file:local.db` and `:memory:` natively — no new dep for DB mock
- `scripts/dev-server.ts` — already Express-based; adding middleware before route registration is straightforward
- All existing `*.test.ts` files use `vi.mock('./client.js', ...)` — this pattern must be preserved; the `client.ts` conditional must not break existing test mocks

### Established Patterns
- `dotenv.config({ path: '.env.local' })` already called in `dev-server.ts` — `MOCK_SERVICES` env var is available there
- `createClient()` call in `client.ts` is the single place to gate on `MOCK_SERVICES`
- Mock route registration in `dev-server.ts` should happen **before** `collectRoutes()` registers real API handlers (route order matters in Express — first match wins)

### Integration Points
- Vite config (`vite.config.ts`) needs to expose `VITE_MOCK_SERVICES` for the frontend to show the dev mode indicator
- The seeded admin user must match the JWT secret in `.env.local` so the mock OAuth bypass produces a valid session token
- `dev.db` goes in the `apps/web/` directory root (same directory where dev server runs); add to `.gitignore`

</code_context>

<specifics>
## Specific Ideas

- **Mock route registration order:** In `dev-server.ts`, register GitHub fixture routes as Express middleware BEFORE `collectRoutes()` loops over the real API handlers. This way `GET /api/github/repos/:owner/:repo/issues` is handled by the mock without touching the real handler.
- **Seed admin user:** Seed script creates a user with `role='admin'`, `github_login='dev-admin'`, `github_token='mock-token'`. Mock OAuth bypass sets a JWT for this user so the frontend auth flow works end-to-end.
- **`VITE_MOCK_SERVICES` pattern:** Vite only exposes env vars prefixed with `VITE_`. The seed script and dev-server.ts use `MOCK_SERVICES` (server-side); the React frontend uses `import.meta.env.VITE_MOCK_SERVICES` for the dev mode banner.
- **Dev mode banner:** A small fixed banner (e.g., top-right corner, amber background, "Dev Mode") that appears when `import.meta.env.VITE_MOCK_SERVICES === 'true'`. Purely cosmetic — no i18n needed (dev-only UI).

</specifics>
