## Summary

Phase 04.2 delivers a fully self-contained local dev environment for `apps/web/`. All key
integration points have been inspected in the live codebase. The implementation surface is
well-contained: three TypeScript files are modified/created (`client.ts`, `dev-server.ts`,
`vite.config.ts`), two new script files are created (`scripts/seed.ts`,
`scripts/mocks/github-fixtures.ts`), and a new React component (`DevModeBanner`) is added to
`App.tsx`. The root `CLAUDE.md` receives a new section.

`@libsql/client` file mode is verified working in this project (`file mode OK` confirmed via
live test). Existing `vi.mock('./client.js')` test patterns are decoupled from `client.ts`
internals — the MOCK_SERVICES conditional is safe to add without breaking any test. Migration
SQL runs identically on SQLite file-mode as on Turso — no schema changes needed.

The trickiest integration point is the mock OAuth bypass: it must call `createToken()` from
`api/_lib/auth/jwt.ts` with the seeded admin user's `id`, `email`, and `role`, then redirect to
`/?token=<jwt>`, exactly replicating what the real `callback.ts` handler does. The `JWT_SECRET`
in `.env.local` must be set so tokens survive across dev-server restarts.

**Primary recommendation:** Gate on `process.env.MOCK_SERVICES === 'true'`. Never modify real
source API handlers — all mocking lives in `scripts/` only.

### Pattern 1: MOCK_SERVICES Gate in client.ts

**What:** Conditional `createClient()` call — `file:dev.db` when mock mode, real Turso otherwise.

**When to use:** Any time the DB client is initialized.

**Critical constraint:** The existing `vi.mock('./client.js', () => ({ getClient: () => ({ execute: mockExecute }) }))` pattern in test files replaces `client.js` entirely — the mock never reaches the `if (MOCK_SERVICES)` branch. Tests are safe. [VERIFIED: triage.test.ts, tasks.test.ts, products.test.ts]

**Example:**
```typescript
// Source: apps/web/api/_lib/db/client.ts — proposed change
export function getClient(): Client {
  if (!client) {
    if (process.env.MOCK_SERVICES === 'true') {
      client = createClient({ url: 'file:dev.db' });
    } else {
      client = createClient({
        url: process.env.TURSO_DATABASE_URL!,
        authToken: process.env.TURSO_AUTH_TOKEN,
      });
    }
  }
  return client;
}
```

**Key detail:** `dev.db` path is relative — when dev-server runs from `apps/web/`, it resolves to `apps/web/dev.db`. The `apps/web/.gitignore` already contains `*.db` [VERIFIED: .gitignore line 6], so `dev.db` is already excluded from git with no further changes needed.

### Pattern 3: Mock OAuth Bypass

**What:** The `GET /api/auth/github/callback` mock must replicate exactly what `callback.ts` does after a successful real OAuth flow: create/find the seeded admin user, issue a JWT, redirect to `/?token=<jwt>`.

**Critical:** `jwt.ts` uses `process.env.JWT_SECRET` and falls back to a random secret per process restart if unset. For mock tokens to survive restarts, `.env.local` **must** set `JWT_SECRET`. Document this as a setup requirement.

**The mock bypass flow:**
```typescript
// scripts/mocks/github-fixtures.ts — proposed mock OAuth bypass
import { createToken } from '../../api/_lib/auth/jwt.js';
import { upsertOAuthUser, userCount } from '../../api/_lib/db/users.js';
import { ensureDb } from '../../api/_lib/db/client.js';

async function mockOAuthCallback(req: Request, res: Response) {
  await ensureDb();
  // Seed admin user if not exists, or fetch existing
  const count = await userCount();
  const user = await upsertOAuthUser({
    githubId: 'mock-12345',
    email: 'dev-admin@github.invalid',
    name: 'Dev Admin',
    githubLogin: 'dev-admin',
    githubToken: 'mock-token',
    role: count === 0 ? 'admin' : 'member',
  });
  const jwt = createToken(user.id, user.email, user.role);
  res.redirect(302, `/?token=${jwt}`);
}
```

**Note:** `upsertOAuthUser` uses `ON CONFLICT(email) DO UPDATE` [VERIFIED: users.ts L89-96] — calling it multiple times is safe (idempotent).

### Anti-Patterns to Avoid

- **Modifying real API handler files:** The mock layer is in `scripts/` only. Real `api/` files must not contain `if (MOCK_SERVICES)` branches.
- **Using `:memory:` DB in mock mode:** File mode (`file:dev.db`) persists across restarts; `:memory:` would wipe seed data on each restart.
- **Registering mock routes AFTER collectRoutes():** Express first-match wins — mocks must be registered before real handlers or real handlers handle the requests first.
- **Omitting JWT_SECRET from setup docs:** Without a stable `JWT_SECRET`, the mock OAuth bypass issues tokens that expire on dev-server restart (random secret per restart). Document it.
- **Using production faker quantities:** 30-50 issues per product is enough. More creates slow seed runs. Less risks missing filter/pagination edge cases.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Fake data generation | Custom random string functions | `@faker-js/faker` with `faker.seed()` | Handles determinism, locale-aware names, URLs, dates, hex colors |
| SQLite for dev | Custom file-backed mock | `@libsql/client` file mode | Already installed; same API as Turso — zero code divergence in DB layer |
| Express route matching | Custom regex | Express `.get()` with `:param` | Already used in dev-server.ts; consistent with existing patterns |

**Key insight:** The entire mock surface is a thin wrapper around existing infrastructure. Nothing genuinely new is built — the work is wiring existing pieces together with an env-var gate.

## Common Pitfalls

### Pitfall 1: Mock Route Path Mismatch

**What goes wrong:** Fixture routes registered as `/api/github/repos/:owner/:repo/issues` but the real handler is at `/api/github/repos/[owner]/[repo]/issues.ts`. In Express the bracket syntax does NOT work — `toExpressRoute()` converts it to `:owner`/`:repo` [VERIFIED: dev-server.ts L52]. But mock routes registered directly as Express routes must use `:owner`/`:repo` too.

**Why it happens:** Developers copy the file path pattern instead of the Express pattern.

**How to avoid:** In `github-fixtures.ts`, register as `app.get('/api/github/repos/:owner/:repo/issues', ...)` — colon syntax, not bracket syntax.

**Warning signs:** Mock route registrations show in logs but requests still hit the real handler (returning 500 due to missing `GITHUB_TOKEN`).

### Pitfall 2: `migrated` Module-Level Cache Across Test Runs

**What goes wrong:** `client.ts` has `let migrated = false` at module level. If the module is imported in both test environment AND mock/dev environments, the cache may bleed.

**Why it happens:** Node.js module cache is process-wide.

**How to avoid:** In the seed script, after calling `ensureDb()`, rely on the cache — it is correct behavior (migrations run once per process). This is only a pitfall if tests somehow share the same process as the dev server, which they don't.

**Warning signs:** "Applied migration" log messages appearing during seed reruns (means cache reset — fine). Absence of those messages on first run would indicate a bug.

### Pitfall 3: Seed Idempotency

**What goes wrong:** Running the seed script twice creates duplicate products/users (failing UUID UNIQUE constraints).

**Why it happens:** `INSERT` without conflict handling.

**How to avoid:** Use `INSERT OR IGNORE` (SQLite) or delete-and-reinsert pattern at seed start. Recommended: `DELETE FROM tasks; DELETE FROM products; DELETE FROM users;` at the top of the seed, then re-insert. Wrap in a transaction for atomicity.

**Warning signs:** Seed fails on second run with `UNIQUE constraint failed` error.

### Pitfall 4: `pr_created` Tasks Missing Required Fields

**What goes wrong:** `rowToTask()` throws `DB integrity: pr_created task X is missing required GitHub fields` [VERIFIED: tasks.ts L65-78].

**Why it happens:** Seed creates `pr_created` tasks without `github_issue_number`, `github_issue_url`, `github_repo`.

**How to avoid:** Seed must supply all three fields for every `pr_created` task. Use consistent fake repo strings matching the product sources.

**Warning signs:** Kanban board renders blank or errors when loading tasks.

### Pitfall 5: JWT Secret Drift

**What goes wrong:** Dev mode login works, then stops working after dev-server restart. JWT from mock OAuth is invalid.

**Why it happens:** `jwt.ts` uses `crypto.randomBytes(32)` as fallback when `JWT_SECRET` is not set [VERIFIED: jwt.ts L3-9].

**How to avoid:** Document that `.env.local` MUST include `JWT_SECRET=any-long-random-string` for mock mode. The seed script could emit a warning if `JWT_SECRET` is not set.

**Warning signs:** Auth store shows logged in, then immediately falls back to login page on page refresh.

### Pitfall 6: Vite Not Picking Up MOCK_SERVICES

**What goes wrong:** `import.meta.env.VITE_MOCK_SERVICES` is `undefined` in the browser even though `.env.local` has `MOCK_SERVICES=true`.

**Why it happens:** Vite only exposes `VITE_`-prefixed vars natively. `MOCK_SERVICES` (without prefix) is not auto-exposed.

**How to avoid:** The `define` block in `vite.config.ts` explicitly maps `import.meta.env.VITE_MOCK_SERVICES` from `process.env.MOCK_SERVICES`. Vite must be restarted after changing `.env.local`.

**Warning signs:** Dev mode banner never appears.

### Faker seed script skeleton

// Source: apps/web/scripts/seed.ts (to create)
import { faker } from '@faker-js/faker';
import { ensureDb } from '../api/_lib/db/client.js';
import { v4 as uuid } from 'uuid';

faker.seed(12345);

async function seed() {
  const db = await ensureDb();

  // Clear existing data (idempotent re-runs)
  await db.executeMultiple(`
    DELETE FROM issue_triage;
    DELETE FROM tasks;
    DELETE FROM task_order;
    DELETE FROM products;
    DELETE FROM users;
  `);

  // Seed admin user
  const adminId = uuid();
  await db.execute({
    sql: `INSERT INTO users (id, email, name, role, github_login, github_token)
          VALUES (?, ?, ?, ?, ?, ?)`,
    args: [adminId, 'dev-admin@github.invalid', 'Dev Admin', 'admin', 'dev-admin', 'mock-token'],
  });

  // Seed products (3)
  for (let i = 0; i < 3; i++) {
    const productId = uuid();

    });
    // ... seed tasks and issue_triage for this product
  }
}

seed().catch(console.error);

## Open Questions

1. **Seed script `MOCK_SERVICES` guard**
   - What we know: Seed writes to `dev.db` via `getClient()` which gates on `MOCK_SERVICES=true`
   - What's unclear: Should the seed script force-set `MOCK_SERVICES=true` internally, or require it in the environment?
   - Recommendation: Seed should load `.env.local` via `dotenv` (same as dev-server) and exit with a clear error if `MOCK_SERVICES !== 'true'` — prevents accidental seeding of the real Turso DB.

2. **Mock OAuth path for `GET /api/auth/github` (initiate)**
   - What we know: D-06 lists this as needing a mock. The real handler [VERIFIED: api/auth/github.ts] redirects to `github.com/login/oauth/authorize` and fails if `GITHUB_CLIENT_ID` is not set.
   - What's unclear: Should the mock `GET /api/auth/github` redirect directly to `/api/auth/github/callback?mock=true`, or should the LoginPage detect mock mode and link directly to the callback?
   - Recommendation: Register `GET /api/auth/github` in mock middleware as a redirect to `GET /api/auth/github/callback` (no state cookie check needed since callback is also mocked). This is the simplest path — keeps `LoginPage.tsx` unchanged.

3. **`VITE_MOCK_SERVICES` via `envPrefix` vs `define`**
   - What we know: Both approaches work in Vite 7 [ASSUMED: based on Vite docs patterns].
   - What's unclear: Whether `loadEnv` in vite.config.ts is needed to forward the variable.
   - Recommendation: Use `define: { 'import.meta.env.VITE_MOCK_SERVICES': JSON.stringify(process.env.MOCK_SERVICES ?? 'false') }` — explicit, no indirection.
